## 3.9 LPI hang root-cause analysis (offline, 05:20)

- sirius DTS chain (sirius->sdm710->sdm670) leaves `lpi_tlmm` disabled; only
  `sdm670-google-common` (Pixel3a, NOT included by sirius) enables it. So all
  previous good boots had LPI OFF; mic6 (first enable, zero pin changes) hung =>
  the CONTROLLER PROBE itself freezes the SoC, not any pin state.
- Mainline driver (`pinctrl-sdm670-lpass-lpi` via `pinctrl-lpass-lpi.c`) does
  direct MMIO to 0x62b40000 with NO clocks/power in DT (pm_clk finds none) and no
  power-domain handling. Downstream uses a different driver (`qcom,lpi-pinctrl`,
  `reg = <0x62b40000 0x0>`) which most likely does NOT touch registers directly
  (size 0!) but routes pinmux via the ADSP. => APPS-direct LPI access is not
  viable on sirius (XPU lockdown and/or LPASS-island power owned by ADSP/TZ).
- Consequence: DMIC (needs LPI gpio26-29 dmic func) is BLOCKED on mainline until
  LPI access is solved (SCM/TZ path, power-domain sequencing, or ADSP-side mux).
  Do NOT retry `lpi_tlmm` enable or `cdc_dmic_default` without a new theory.
- Pixel3a comparison is moot (different XPU/TZ + different ADSP fw behaviour).
