## 3. WiFi 诊断全记录（为什么 parked）

一句话：**驱动和 DT 都没问题，问题是 `wlanmdsp` 没人带起来，QRTR 上永远没有 WLFW。**

- 7.2 `ath10k_snoc` probe 成功后只做 `qmi_add_lookup(WLFW)` 干等，“绑定成功但无日志”是正常 QMI 行为，不是 bug。
- `qrtr-lookup` 实测 QRTR 通，ADSP node5 服务全在，唯独无 WLFW。
- 7.2 全树零处加载 `wlanmdsp.mbn`；`wifi-firmware` DT 子节点只建 IOMMU 映射，不绕过 TZ。
- 非 7.2.3 回归：7.0.10 同样到不了 WLFW。上游老内核是“初始化完再 XPU crash”，本树是“WLFW 根本不出现”，两码事。

DT 两次迭代：

- v1：`wifi-firmware` 子节点 SID `0x40` → probe `-EINVAL`。
- v2：SID 改 **`0x42`**（规律：wifi SID+2，同 sc7180 `0xc0→0xc2`）+ `calibration-variant=xiaomi_sirius` → probe 干净（`use_tz=0`，fw-pdev + IOMMU 正常）。已提交 `847e9daf` 并刷机验证。

## 12. 2026-09-19 夜：基带(MPSS) bring-up 与 rmtfs 发现（WiFi 仍未通）

结论先行：**WiFi 卡点已从"驱动/DT"收敛到"WLAN 固件由基带的 wlan_pd 加载，而 wlan_pd 至今没起来"**。
主线 ath10k 那条链（probe / MSA / IOMMU / XPU / BDF / wlan_enable）都是现成的，不用移植安卓的 qcacld/icnss。

### 12.1 WiFi 启动链（本机实测 + 源码核对）

1. bootloader/PMIC 先把 WCN 的几路电放开（boot-on）。
2. AP 内核 `qcom_q6v5_mss` 加载基带：`mba.mbn` → TZ PAS 认证 → `modem.mbn`(.mdt 头 + `.b00..b29` 分片) → 认证 → `remote processor is now up`。
3. **基带固件里的 PD**（modem.mbn 内含 `msm/modem/wlan_pd`、`wlan_process`、`wlanmdsp.mbn`、
   `/readonly/firmware/image/wlanmdsp.mbn`、`/readonly/vendor/firmware/wlanmdsp.mbn`）负责把 WLAN 固件拉起来。
   主线 ath10k 也印证这点：`ath10k_snoc_modem_notify()` / `ATH10K_SNOC_FLAG_MODEM_STOPPED`（上游 commit 747ff7d3d742）。
4. WLAN 固件起来后要在 QRTR 注册 WLFW（QMI service 0x45 = 69）；AP 侧 `ath10k_snoc` 在 probe 时就
   `qmi_add_lookup(WLFW)` 干等，服务一到才继续：ind_register → host_cap → msa_mem_info →
   `qcom_scm_assign_mem`(HLOS→MSS_MSA/WLAN/WLAN_CE) → msa_ready → cap → BDF(board-2.bin, variant
   `xiaomi_sirius`) → cal report → FW_READY → `ath10k_core_register/start` → `hif_power_up`
   (regulator_bulk_enable + QMI `wlan_enable`) → wlan0。
5. 备注：`firmware-5.bin` 对 WCN3990 只有 **60 字节**（stub），真固件是 `wlanmdsp.mbn`(3MB)，由基带那条路加载；
   蓝牙走 UART+btqca（`crbtfw21.tlv`），与 WiFi 无关。

### 12.2 本轮做了什么

- 干净 ath10k 模块：`/lib/modules/7.2.3-sdm670-gcbbdbeb2ca53/.../ath10k_snoc.ko.zst` 已是匹配版
  (md5 `9d5c8c29a826923798713bafd38f0035`, vermagic `7.2.3-sdm670-gcbbdbeb2ca53`)，
  只需 `rmmod/insmod` 把运行中的 diag 版换掉。
- 基带固件：**从设备自己的 modem 分区(只读挂载)复制**到 `/lib/firmware/qcom/sdm710/pyxis/`：
  `mba.mbn`(md5 `62520866a13dc47bd0460f7594cfd395`) + `modem.mbn`(=分区 `image/modem.mdt`) +
  `modem.b00..b29`（主线 mdt_loader 原生支持这种 "modem.mbn 头 + modem.bXX 段" 布局）。
  注意：服务器 `firmware/pyxis-dsp/mba.mbn` 与本机分区里的 **md5 不一致**(`c658ad50...`)，不要用服务器那份。
- **rmtfs 是缺失的关键服务**：`/dev/qcom_rmtfs_mem1` 在，但手机没装 rmtfs → 基带 EFS 请求无人应答 →
  基带 PD 卡死 → ~40s 被看门狗打死 → crash/recover 循环（日志 `fatal error without message`）。
  装上 `rmtfs` 1.1-4 后循环停止。
- rmtfs 配置（Debian 默认 `-r -P` 在本机是错的：它去找 `/dev/disk/by-partlabel/modem_fs1`，
  本机分区名是 `modemst1`）。改成：
  `/etc/systemd/system/rmtfs.service.d/override.conf` →
  `ExecStart=/usr/bin/rmtfs -r -s -o /var/lib/rmtfs`，
  并在 `/var/lib/rmtfs/` 建符号链接：`modem_fs1→modemst1`、`modem_fs2→modemst2`、
  `modem_fsc→fsc`、`modem_fsg→fsg`（对应 rmtfs 内置表 `/boot/modem_fs*`）。
  改完基带不再崩，QRTR node 0 出现**整套基带服务**（EFS/WDS/NAS/UIM/IMS/IPA/Thermal/Coexistence/RFPE/Time/PDS…）。

- ❌ QRTR 仍**没有 WLFW(0x45/69)**，`ath10k_snoc` 仍停在等待，无 wlan0。

  路径既不在 modemst/modemst2/fsg 备份里（已 grep 确认），也不是 rmtfs 现有分区表项（modem 只请求过

### 14.1 证据链（全部实测）

1. crDroid（Android 16，WiFi 正常）上运行的两个关键守护进程：

## 17. 2026-09-19 中午：关机"卡死"解决 —— 不是死锁，是根分区满 + 巨慢（+did 系统性排查记录）

> 现象：WiFi 打通后连续 4 次关机/重启"冻屏"（ping 通、SSH 死），都以长按强制断电收场；
> 一度怀疑 wlan（时间相关性 100%）。
> 结论：**userspace 关机每次都只要几秒、干净走完（Journal stopped 都有）；之后巨慢，
> 根因是根分区 91% 满（5.9G 用 5.1G，只剩 515M，journal 占 606M）+ eMMC 慢。
> `resize2fs` 扩到 50G 后首次关机即成功（慢几分钟但不断电、不冻结）。**
> 另：插着 USB 关机会进充电界面又自动开机（charger mode + 改过的 boot，老行为，非故障）。

### 17.1 排除清单（都查了，都不是）

- userspace：三次 `-b -1` 日志 + 单调时间 gap 分析，关机阶段无 >8s 停顿、无超时 kill，
  每次都到 `Journal stopped`。屏幕冻结点（user@1000/upower/cups）每次不同——fb 在
  `fb_set_par -16` 后早死，屏上位置无意义。
- `ath10k_snoc_shutdown`：关机单元（`wifi-shutdown.service`，disconnect + rmmod，经 wd 验证
  rc=0）每次都跑了，driver 已卸载；且全树 modem/sysmon/sdhci/dwc3 均无 `.shutdown` 回调，
  唯一有的是 ath10k（已摘）。此路排除。
- sysmon/modem stop：全是 5s timeout bounded，无无限等待；且 modem 在 poweroff 路径根本不停。
- BT（`qca_serdev_shutdown` 对 WCN3990 是 no-op）+ `preshutdown_cmd failed (-56)` live 可复现但返回，
  非 hang。BT 洗脱。
- PSCI：`sysrq-b` 紧急复位一次成功 → reset 路径健康；halt 测到 ping 灭（走到 USB 卸载之后）。
- 关联 teardown：WiFi idle（断开）关机依然慢 → 非关联 teardown 问题。
- ADSP recovery 死锁（`rproc_recovery_wq` D-state，`destroy_workqueue←apr_remove←glink_remove`，
  跨快照永久存在）：真实内核 bug，但无等待者，不阻塞关机；已用 udev 规则禁 ADSP recovery
  （`60-adsp-norecovery.rules`，本机验证本启动 `recovery=disabled` 生效、无 D-state），
  属顺手止血，非本次根因。

### 17.2 修法（手机上已执行）

```bash
sudo resize2fs /dev/mmcblk0p81   # 在线扩 5.9G→50G（p81 分区本就是 51G，当初刷完没扩）
sudo journalctl --vacuum-size=120M

# 结果：50G/用 4.5G/剩 43G（10%）
```

另：删 shutdown tracer（自建，每 2s 写 /home，干扰关机）+ tqftpserv 去 `-d`，
+ 新增 `/usr/local/sbin/safe-reboot`（sysrq s+u+b，可靠重启通道）+ `sysctl.d/60-sysrq.conf`。

### 17.3 教训（写进流程）

1. 新 rootfs 第一件事就是 `resize2fs`（`WIFI-ROOTFS-SETUP.md` 已补）。
2. 关机/reboot 给 15 分钟耐心再判死刑；之前几次 force-off 把 fs 越搞越慢，恶性循环。

## 18. 2026-09-19 中午：重启掉时间 —— PMIC RTC 只读 + 无 NTP，fake-hwclock + timesyncd 修

> 现象：每次重启回到 1978-01-06（`timedatectl` 显示 RTC time = 系统时间 = 1978）。
> 修完状态：`NTP service: active`、`System clock synchronized: yes`，WiFi 连上后几十秒自动扶正；
> 离线启动靠 fake-hwclock 从上次关机时间恢复，不再掉回 1978。

### 18.1 根因（两条，查全了）

1. PMIC RTC 对 Linux 只读。`rtc-pm8xxx`（`c440000.spmi:pmic@0:rtc@6000`，pm660）可读
   （`hctosys=1`，开机能把 RTC 读进系统时钟），但 DT（`pm660.dtsi` 的 `rtc@6000`）没写
   `allow-set-time`，驱动走 offset 模式，`RTC_SET_TIME` 直接 `-ENODEV`：
   `hwclock --systohc` 报错 `ioctl(RTC_SET_TIME) ... failed: No such device`。
   上游设计就是 modem/XBL 拥有 RTC，AP 侧 Linux 不许写（服务器已对过驱动源码
   `rtc-pm8xxx.c:622` + `pm660.dtsi:43`）。——所以"写 RTC 持久化"此路不通，
   加 DT 属性要动内核+重刷（无 fastboot），且 XBL 也可能照样覆盖，不值得。
2. 从无对时服务。`systemd-timesyncd`/`chrony`/`fake-hwclock` 全没装，
   `timedatectl` 显示 `NTP service: n/a`、`CanNTP=no`。RTC 每次重启回到 1978，
   系统时间也就跟着 1978。

### 18.2 修法（手机上已执行，全用户态）

```bash
sudo date -s '2026-09-19 12:43:00 +0800'   # 先手动扶正一次（§18.3 解释为什么必须）
sudo apt-get update
sudo DEBIAN_FRONTEND=noninteractive apt-get install -y systemd-timesyncd util-linux-extra fake-hwclock
sudo timedatectl set-ntp true              # 启用 timesyncd，开机自启
sudo fake-hwclock save                     # 把正确时间存 /etc/fake-hwclock.data
```

验证：`timedatectl` → `NTP service: active`、`System clock synchronized: yes`；
`systemctl is-enabled systemd-timesyncd fake-hwclock-load fake-hwclock-save.timer` 全 enabled；
下次重启后看 `timedatectl`（在线：NTP 几十秒扶正；离线：fake-hwclock 从上次时间恢复）。

### 18.3 大坑：1978 时间下 apt 装不上任何包（https 证书全判未生效）

- 现象：`apt-get install` 对三个包全 `Ign` 重试，`dpkg -l` 始终为空。开始误以为源不行，
  看 `/tmp/apt*.log` 才发现是证书时间问题。
- 鸡生蛋：要装 NTP 先过 https，要过 https 先有正确时间。解法就是上面先 `date -s` 手动扶正一次。
- 顺手坑：`sudo pkill -f 'apt-get install'` 会把执行这条命令的 ssh 会话自己也匹配杀掉，
  自杀 pattern 要写 `insta[l]l` 形式。

`WIFI-ROOTFS-SETUP.md` §0.5 已补：扩完分区先 `date -s` 扶正再 `apt`，装包表加
`systemd-timesyncd fake-hwclock`（`util-linux-extra` 提供 hwclock，顺手装，写 RTC 用不上但查 RTC 好用）。

### 18.5 PMIC RTC 能"修"吗（结论：硬件没坏，不必修；真要修有三档）

验证（2026-09-19 13:2x，手机 live）：`since_epoch` 8 秒走 8 秒（252891663→252891671），
计数器自走正常；i2c 值 252.9M 秒≈8.0 年≈本机出厂至今——**RTC 从 2018 年上电就没停过，
既没坏也没重置，只是起点不是 Unix epoch**。显示 1978 是缺"纪元基准"，不是硬件故障
（安卓原生靠 time_daemon 从 modem 取时间，根本不用它；UEFI 机型靠 `RTCInfo` 变量补 offset）。
`hwclock --systohc` 的 ENODEV 来自 `pm8xxx_rtc_update_offset`：无 nvmem cell 又无 UEFI 时
直接 `-ENODEV`（驱动源码已对，`rtc-pm8xxx.c:249`），不是驱动 bug。

- A. DT 加 nvmem cell 存 offset（官方路径，唯一推荐的真修）：`rtc@6000` 加
  `nvmem-cells` 指向掉电不丢的存储，驱动自动"开机读 offset＋显示、set_time 存 offset、
  关机自动存"，硬件计数器本身不动。代价：新分支＋重编＋重刷 boot（无 fastboot，暂堵；
  用哪块 nvmem 如 PMIC SDAM 待调研）。
- B. DT 加 `allow-set-time`（能，但不推荐）：直接把硬件计数器改成 Unix 时间。
  风险：出厂以来没人写过它，modem/XBL 是否依赖未知；同样要重刷。
- C. 内核模块直写 SPMI 0x6000 寄存器绕过驱动（有办法，但别）：PMIC 写错寄存器影响
  充电/温控，且 XBL 若覆盖就白干。已否决。
- D. 现状（已采用）：NTP＋fake-hwclock，思路与安卓 time_daemon 一致，零内核风险，
  在线/离线全覆盖。跨重启计数器是否自走的严格验证：记 `since_epoch=252891671`
  （13:2x），下次自然重启后对比差值≈关机时长即实锤。

### 18.6 选项 A 的终点：pm660 没有 SDAM，此路硬件上不存在（2026-09-19 13:3x）

用户选 A 后深挖的结论：**A 做不了——不是不想，是这块 PMIC 没这块硬件**，故未建新分支（无可提交之物）。

证据链：
1. A 要求 PMIC 里有 SDAM（可写、电池保持）来存 offset。upstream `pm660.dtsi` 无 sdam 节点；
   下游 CAF 系 `pm660.dtsi`（LineageOS sdm710，服务器联网现抓）外设表只有
   revid/misc/pon/temp/gpio/coincell/rtc/vadc/pdphy/adc_tm/pbs/bcl/clkdiv，
   无任何 `0xbxxx` SDAM 节点。
2. 全树 `qcom,spmi-sdam` 用户全是 2019+ PMIC（pmi632/pmk8350/pmk8850/pm8150…），
   2017 年的 pm660 从未出现。
3. 不能硬猜 `0xb600`：若该地址在 pm660 上是别的外设，sdam 驱动写 offset 会误写控制寄存器；
   更糟的是 offset 读失败会导致 rtc probe 直接失败，连现在的 hctosys 都丢掉。
   为一个纯显示问题冒这个险，不可接受。
4. 其他存储全灭：QFPROM 只读；UEFI 在本机不存在（手机验证 `/sys/firmware/efi` 无）；
   RMEM 方案要重编＋重刷（无 fastboot，本来也刷不进去）且只保暖重启、不保断电。

结论：保持 D（NTP＋fake-hwclock）即最优解，日后有 fastboot 且执意要修，
再议 RMEM 半修（不推荐）。

### 18.9 有没有"PC BIOS 时钟那样的东西"（答：没有；安卓没卡一样没时间）

- 最接近 BIOS 时钟的是 PMIC RTC：电池保持、自走正常（§18.5）。但它缺了关键一半——
  出厂就没调过时间，且谁都写不了它（上下游双只读，§18.7）。类比：主板电池有电、
  晶振在走，但出厂时间从没调过，BIOS 设置界面还被锁死了。
- `fake-hwclock` 就是我们的"BIOS 时钟"软件版：eMMC 掉电不丢，存上次关机时间。
  它还有真 RTC 没有的优点：电池抠掉 RTC 归零，它不丢（只怕重刷）。
- MIUI 无卡行为与我们完全一致：开机读 RTC（1978）→time_daemon 拿不到 modem 时间→
  干等→连 WiFi 后靠网络时间扶正。我们复刻了这条链（NTP），外加 fake-hwclock 兜底离线。
- "一次性写 RTC 就永久解决"理论成立（自走正常，写一次 Unix 时间便永远准），
  但要重编＋重刷（无 fastboot），且 PMIC 彻底掉电仍归零，不如 fake-hwclock 硬。
  有 fastboot 后可当小甜点，不值得专门折腾。RTC 问题到此关闭。
